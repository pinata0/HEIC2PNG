# 1. HEIC는 그냥 이미지 한 장 짜리 포멧이 아닐 수 있다

HEIC는 HEIF라는 컨테이너 안에 HEVC로 압축된 이미지를 담는 형태이다.
경우에 따라 한 파일 안에 여러 이미지, 썸네일, depth image, auxiliary image 등이 들어갈 수 있다.

그래서

HEIC 파일
->
컨테이너 파싱
->
어떤 image item을 변환할지 선택
->
HEVC 디코딩
->
raw pixels
->
PNG 인코딩

이런 과정이 된다.

# 2. 브라우저에서 HEVC 디코딩을 직접 구현하기 어렵다.

JavaScript로 직접 HEVC decoder를 구현하는 건 현실적이지 않다.
보통 C/C++ 기반 `libheif` 같은 구현을
WebAssembly로 컴파일해서 브라우저에서 돌린다.

그래서

HEIC 파일
->
libheif (WASM)
->
RGBA pixels
->
Canvas / PNG encoder
->
PNG

이런 구조가 된다.

# 3. 메모리 사용량이 갑자기 크게 증가함

아이폰 사진이 4k 라고 하면
압축된 HEIC 파일은 5MB일지라도

디코딩한 RGBA 픽셀은
4032 x 3024 x 4 bytes = 48.8MB

여기에 HEIC 원본 buffer, decoder 내부 buffer, PNG encoder buffer까지 필요하다

그래서 4MB짜리 파일 하나 처리하는데 실제 RAM은 100MB 가까이 순간적으로 필요할 수 있다.

여러 장을 동시에 변환하면 모바일 브라우저가 죽거나 탭이 강제 종료될 수 있다.
실제 브라우저 변환 라이브러리들에도 성능 관련 이슈가 보고되어 있다.

# 4. 메인 스레드가 멈출 수 있다.

HEVC 디코딩은 CPU 작업이다.

UI thread
- 버튼 클릭
- 드래그앤드롭
- 화면 렌더링
- HEIC decode

저게 동시에 진행되는데
decode에서 CPU를 오래 잡으면 UI가 버벅거린다.

그래서 제대로 만들려면

Main Thread
- UI
- postMessage()
    -> Web Worker
    -> libheif WASM
    -> PNG 생성

이런 식으로 Web Worker에 디코딩을 넘기는 것이 좋다.
heic2any 같은 라이브러리도 브라우저 측 변환에 worker 기반 처리를 사용한다.

# 5. EXIF가 사라질 수 있다.

HEIC 안에는 사진뿐 아니라

촬영 시간
GPS
카메라 모델
회전 정보
노출
ISO
색 공간

같은 메타데이터가 들어간다.

단순히

HEIF
->
pixel decode
->
PNG encode

해버리면 픽셀만 복사되고 metadata는 사라진다.

# 6. 회전 문제가 생긴다.

카메라 이미지는 픽셀 자체가 돌려져 있는 게 아니라

pixels : 4032 x 3024

EXIF:
Orientation = 6
-> 화면에 표시할 때 90도 회전
같은 방식일 수 있다.

그래서 변환하고 회전되어 출력되는 문제가 나올 수 있다.

# 7. 색깔이 달라진다

아이폰은 Display P3 같은 넓은 색 영역을 사용하는 경우가 있다.

변환 과정에서 색공간 정보를 잘못 처리하면 색이 조금 탁해지거나 어두워질 수 있다.

# 8. 파일이 엄청 커질 수 있다.

HEIC는 사진에 특화된 손실압축을 사용하고
PNG는 무손실압축이다.

이미 HEIC에서 압축 과정이 한 번 있었기 때문에
PNG로 바꾼다고 잃어버린 디테일이 복원되는 것은 아니다.
